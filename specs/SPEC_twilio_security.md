## Overview

Adds two authentication layers to the Sofia voice backend: (1) HMAC-SHA1 signature validation on the `/twiml` HTTP webhook using Twilio's `X-Twilio-Signature` header, and (2) a shared-secret token passed through a Twilio `<Stream><Parameter>` element and validated on the `/twilio-media` WebSocket before any audio is relayed. Both layers are hard prerequisites for Fly.io deployment — an unauthenticated public `/twiml` + `/twilio-media` is a credit-drain vector the moment the Fly hostname is known.

## Dependency decision — twilio SDK vs. manual HMAC

**Decision: manual HMAC. Do NOT add the `twilio` npm package.**

Argued both sides:

| Factor | `twilio` SDK `validateRequest()` | Manual HMAC-SHA1 |
|--------|----------------------------------|------------------|
| Correctness | Canonical reference implementation, kept in sync with Twilio backend | We implement the documented algorithm (well-specified, rarely changes) |
| Dependency weight | ~4MB, pulls `axios`, `qs`, `xmlbuilder`, `jsonwebtoken`, `scmp` — Sofia uses **none** of it today | Zero deps, ~25 LOC |
| Attack surface | Transitive: any CVE in `axios` or subdeps becomes ours | Only Node stdlib `crypto` |
| Future Twilio API changes | SDK absorbs them automatically | HMAC algorithm is a published spec; has not changed since at least 2013. If Twilio deprecates SHA1 → SHA256, we update one line |
| Ecosystem fit | Becomes useful *later* when we start sending SMS via Twilio REST | Netlify lead-function already uses raw `fetch` to Twilio REST, so precedent is "no SDK" |
| Testability | Larger mock surface | Trivial: known input → known digest |

The SDK would only become compelling if we start doing REST calls to Twilio from backend (creating subaccounts, provisioning numbers, etc.). We don't; Netlify does, and it uses raw `fetch`. Bringing in the full SDK for a 25-LOC HMAC is not proportional. If that changes, add the SDK in a separate PR and swap the validator implementation — the middleware signature stays the same, so it's a one-file change.

**The manual implementation follows Twilio's published algorithm:**
1. Take the full request URL as Twilio sees it (see §1.3).
2. Sort POST parameters alphabetically by key.
3. Append each `key + value` to the URL (no separator).
4. HMAC-SHA1 with `TWILIO_AUTH_TOKEN` as key.
5. Base64-encode the digest.
6. Compare (constant-time) against `X-Twilio-Signature` header.

Reference: https://www.twilio.com/docs/usage/webhooks/webhooks-security

## API contracts

### `middleware/twilio-signature.js`

```js
// Signature: factory returning a Fastify preValidation hook
export function makeTwilioSignatureHook({ authToken, log, counters, trustedProxy = true }): FastifyHookFn
```

**Input (at runtime, per request):**
- `request.raw` (Node IncomingMessage) — for method, headers
- `request.headers['x-twilio-signature']` — string | undefined
- `request.body` — string (raw, unparsed form body; see §1.4 about body parser)
- `request.url`, `request.headers['host']`, `request.headers['x-forwarded-proto']`, `request.headers['x-forwarded-host']`

**Output:**
- On success: calls `done()` / returns without reply. Control passes to route handler.
- On failure: sends HTTP `403`, empty body (no text, no JSON), logs a structured warn, increments `counters.authRejectionsTotal`. Returns without invoking handler.

**Error cases (all → 403, no body):**
| Case | `reason` logged | Counter label |
|------|----------------|---------------|
| Header missing | `"no-header"` | `no_header` |
| `TWILIO_AUTH_TOKEN` not configured (should be caught at boot, defensive) | `"server-misconfigured"` | `server_misconfigured` |
| Body not a string (content-type mismatch) | `"body-not-string"` | `bad_body` |
| Computed signature ≠ header (constant-time compare) | `"bad-sig"` | `bad_sig` |

**Never log:** the signature value, the Auth Token, the full body. Log only `reqId`, `route`, `reason`, `sourceIp` (from `request.ip`, which Fastify derives from `X-Forwarded-For` when `trustProxy` is on).

### `middleware/ws-auth.js`

```js
// Signature: pure validator, called synchronously after Twilio sends the "start" event
export function validateStreamAuth({
  customParameters,   // object | undefined from msg.start.customParameters
  expectedToken,      // string from env
  log,
  counters,
  reqId,              // correlation id from the WS upgrade
  sourceIp
}): { ok: true } | { ok: false, reason: 'no-token' | 'bad-token' | 'server-misconfigured' }
```

**Input:**
- `customParameters`: the object Twilio delivers on the `start` frame. Shape:
  ```json
  { "auth_token": "k3Jq8vR2mN7pX9wQ5tY1aB4cD6eF0gHz" }
  ```
  Keys are strings, values are strings. Twilio lowercases custom parameter names in some SDK versions — validator MUST look up the key case-insensitively (check both `auth_token` and `authToken`; prefer `auth_token`).

**Output:** `{ ok: true }` or `{ ok: false, reason }`.

**Behavior:** constant-time string compare (`crypto.timingSafeEqual` on equal-length Buffers; if lengths differ, return bad-token without comparing). On `ok: false`, caller closes WS with code **1008 (Policy Violation)** and an empty reason string; does not consume further frames.

**Never log:** the received token, the expected token. Log `reqId`, `route: "/twilio-media"`, `reason`, `sourceIp`.

## 1. HTTP webhook signature validation

### 1.1 Where the hook runs

Install as a **`preValidation`** hook scoped to `/twiml` only (not global). `preValidation` runs after body parsing but before route handler, which is exactly what we need: we have the parsed form body AND the raw body (the existing custom parser in `server.js` stores the raw string as `request.body` because `parseAs: 'string'` is set). We do NOT use `preHandler` — signature validation must gate the handler entirely, and `preValidation` is the earliest hook where the body is guaranteed available.

Installation in `server.js`:

```js
import { makeTwilioSignatureHook } from './middleware/twilio-signature.js';
// ...
const twilioSigHook = makeTwilioSignatureHook({
  authToken: process.env.TWILIO_AUTH_TOKEN,
  log: fastify.log,
  counters,
});

fastify.post('/twiml', { preValidation: twilioSigHook }, twimlHandler);
```

Also change `fastify.all('/twiml', ...)` → `fastify.post('/twiml', ...)`. Twilio sends POST. `all` invites GETs from curious humans hitting the URL; they should get a 404, not a handler invocation. If a GET slips through during debugging, the signature hook will 403 it anyway (no header), but `post` is more honest.

### 1.2 Body parser interaction

The existing parser captures raw body as a string:

```js
fastify.addContentTypeParser('application/x-www-form-urlencoded', { parseAs: 'string' }, (req, body, done) => {
  done(null, body);  // <-- body is the raw string
});
```

This is correct for signing but means the route handler itself receives a string, not a parsed object. The signature middleware parses it internally using `new URLSearchParams(request.body)` to get the sorted params. The route handler today doesn't read form fields, so no change is needed there; if future work needs them, parse at the handler or flip the parser to return a parsed object **after** the hook has already used the raw string for validation (not clean — prefer keeping raw-string capture + parse-on-demand).

### 1.3 URL reconstruction behind Fly's proxy

Twilio signs the exact URL it sent the POST to. Fly.io terminates TLS at its proxy and forwards HTTP to the Node process. Naive use of `request.protocol` returns `http` even when the public request was `https://`. We MUST reconstruct the URL as Twilio sees it.

**Algorithm (in order of preference):**

```js
function reconstructUrl(request) {
  const xfProto = request.headers['x-forwarded-proto'];   // "https" on Fly
  const xfHost  = request.headers['x-forwarded-host'];    // often absent on Fly
  const host    = xfHost || request.headers['host'];      // fall back to Host
  const proto   = xfProto || request.protocol;             // fall back to Fastify's guess
  // request.url is the path+query portion, e.g. "/twiml"
  return `${proto}://${host}${request.url}`;
}
```

**Trust-proxy setup required:** Fastify must be configured with `trustProxy: true` (or a specific CIDR allowlist if we want to be precise — Fly's proxy sits on the machine's private network, so `true` is fine here). Without this, `request.ip` returns the Fly proxy's internal IP instead of the caller's, and some Fastify internals ignore `X-Forwarded-*`. Change `Fastify({ logger: true })` → `Fastify({ logger: true, trustProxy: true })`.

**Edge case — local dev without a proxy:** `X-Forwarded-Proto` won't be present, `request.protocol` returns `http`, `host` is `localhost:3000`. Twilio won't hit localhost directly (ngrok is in front in dev), but ngrok DOES set `X-Forwarded-Proto: https`. So the same code works in both environments.

**Edge case — port in Host header:** When Twilio signs `https://sofia-voice.fly.dev/twiml`, there's no port. When ngrok forwards, the Host header is the ngrok hostname without port. Don't append a port ourselves. Just use the Host header verbatim. If a port ever leaks in (e.g., someone calls with explicit `:443`), signature fails and we reject — that's the right outcome; Twilio won't do that.

**Do NOT** try both URL variants (http and https) and accept either. Twilio is unambiguous about what it signed; accepting either is a downgrade-attack surface.

### 1.4 Signature computation

```js
import crypto from 'node:crypto';

function computeSignature({ authToken, url, bodyString }) {
  const params = new URLSearchParams(bodyString);
  const sortedKeys = [...params.keys()].sort();
  let payload = url;
  for (const key of sortedKeys) {
    payload += key + params.get(key);
  }
  return crypto
    .createHmac('sha1', authToken)
    .update(payload, 'utf8')
    .digest('base64');
}

function safeEqual(a, b) {
  const ab = Buffer.from(a, 'utf8');
  const bb = Buffer.from(b, 'utf8');
  if (ab.length !== bb.length) return false;
  return crypto.timingSafeEqual(ab, bb);
}
```

- `URLSearchParams` handles URL-decoding correctly, which matches what Twilio signed (the raw POST body is percent-encoded; Twilio signs the decoded values).
- If a key appears multiple times, Twilio's spec says concatenate all occurrences in order. `URLSearchParams.getAll(key)` returns them in order; iterate through each value. **Implementation detail for the Coder:** use `getAll`, not `get`:
  ```js
  for (const key of sortedKeys) {
    for (const val of params.getAll(key)) {
      payload += key + val;
    }
  }
  ```
  Then dedupe `sortedKeys` (a Set) before iterating, since `keys()` yields duplicates.

### 1.5 Behavior on missing `TWILIO_AUTH_TOKEN`

**Decision: refuse to start.** In `server.js`, before `fastify.listen()`, assert that `process.env.TWILIO_AUTH_TOKEN` is a non-empty string. If missing, log `fatal: TWILIO_AUTH_TOKEN not set` and `process.exit(1)`.

Rejected alternative (run-but-reject-all): silent fail. A dev who forgot to set the var would see the server running and Twilio callbacks returning 403, and waste 20 minutes diagnosing. Hard-fail at boot makes the misconfiguration loud.

Same rule for `STREAM_AUTH_TOKEN`. Both checks in the same boot block:

```js
for (const key of ['TWILIO_AUTH_TOKEN', 'STREAM_AUTH_TOKEN']) {
  if (!process.env[key] || process.env[key].length < 16) {
    fastify.log.fatal({ key }, 'Required secret missing or too short; refusing to start');
    process.exit(1);
  }
}
```

The `length < 16` check catches placeholder values like empty strings or obvious typos. Real Twilio tokens are 32 hex chars; our generated stream token is ≥32 chars.

### 1.6 Response on failure

HTTP `403`, empty body, `Content-Length: 0`. **Do not** return JSON, do not return a Twilio-ish XML error — we want to leak zero information about whether the endpoint exists or what failed. Twilio, when signature mismatches, would never receive 403 in practice (its own signatures are valid); humans probing get a blank 403.

Headers: standard Fastify defaults. Do not add a `WWW-Authenticate` header — we're not HTTP-auth-challenging.

## 2. WebSocket Media Stream authentication

### 2.1 Pattern decision

**Decision: Option (b) — shared secret in `<Stream><Parameter>`.**

Evaluation of the three options:

| Option | Pros | Cons | Verdict |
|--------|------|------|---------|
| (a) Signed URL with short-lived token in query string | Nothing to configure on Twilio side beyond the URL; token auto-rotates per call | Token must be minted per `/twiml` response → introduces coupling and cache issues. Token appears in logs (URL is in access logs). Fly log drain would capture tokens forever. Rotation requires a clock. | **No** — logging leak is the killer. |
| (b) Shared secret via `<Parameter name="auth_token" value="..."/>` inside `<Stream>` | Secret travels in the WS start-frame payload (JSON body over an established TLS connection), not in URL. Never appears in access logs. Trivial to validate. Rotatable by changing env var + redeploy. | Static secret — a compromise requires rotation. Same secret for all calls within a deploy. | **Yes** — best log posture, simplest code. |
| (c) IP allowlist of Twilio's CIDR ranges | No secrets to manage | Twilio's CIDRs can change without formal notice; we'd need to fetch/update them. Gives no defense against an attacker who pivots through an AWS region Twilio also uses. Defense-in-depth bar is "layer," not "only fence." | **No as primary**, could be a future add-on layer. |

Option (b) justifies itself on three axes: (1) **logging hygiene** — the token never touches any URL or access log; (2) **simplicity** — no token-minting clock, no per-request state; (3) **rotation story** — change `STREAM_AUTH_TOKEN` secret + `fly deploy`; next call picks up the new token because `/twiml` embeds it at response-build time.

### 2.2 How the token lives in TwiML

`/twiml` response changes from:

```xml
<Response>
  <Connect>
    <Stream url="wss://sofia-voice.fly.dev/twilio-media" />
  </Connect>
</Response>
```

to:

```xml
<Response>
  <Connect>
    <Stream url="wss://sofia-voice.fly.dev/twilio-media">
      <Parameter name="auth_token" value="k3Jq8vR2mN7pX9wQ5tY1aB4cD6eF0gHz"/>
    </Stream>
  </Connect>
</Response>
```

Twilio delivers the parameter on the `start` event as `msg.start.customParameters.auth_token`. (In some Twilio clients the casing differs; validator is case-insensitive on the parameter name — see §2.4.)

The `value` attribute must be **XML-escaped**. Our generated token is URL-safe base64 (`A-Za-z0-9_-`), which contains no XML special chars, so escaping is a no-op in practice — but the handler must still escape defensively in case a future token format includes `&`, `<`, `>`, `"`, or `'`. Minimal escape function:

```js
function xmlAttrEscape(s) {
  return s.replace(/&/g, '&amp;').replace(/</g, '&lt;').replace(/>/g, '&gt;').replace(/"/g, '&quot;').replace(/'/g, '&apos;');
}
```

Handler:

```js
fastify.post('/twiml', { preValidation: twilioSigHook }, async (req, reply) => {
  const host = req.headers['x-forwarded-host'] || req.headers.host;
  const protocol = host?.includes('localhost') ? 'ws' : 'wss';
  const wsUrl = `${protocol}://${host}/twilio-media`;
  const token = xmlAttrEscape(process.env.STREAM_AUTH_TOKEN);
  reply.type('text/xml');
  return `<?xml version="1.0" encoding="UTF-8"?>
<Response>
  <Connect>
    <Stream url="${wsUrl}">
      <Parameter name="auth_token" value="${token}"/>
    </Stream>
  </Connect>
</Response>`;
});
```

### 2.3 Secret generation, rotation, storage

- **Generation (one-time, Parviz):** `openssl rand -base64 32` → 44 chars (ending in `=`). Strip trailing `=` and replace `+`/`/` with `-`/`_` if desired, or leave as-is (XML-escape will handle `+` and `/`; `=` is harmless). Minimum acceptable length: 32 bytes of entropy = 43 base64 chars.
- **Storage:** `fly secrets set STREAM_AUTH_TOKEN=...`. Never in git, never in image, never in logs.
- **Rotation policy:** No automatic rotation for v1. Rotate on (a) any suspected compromise, (b) any team member with access to Fly secrets departing. Rotation procedure:
  1. `fly secrets set STREAM_AUTH_TOKEN=<new value>` — Fly restarts the machine, which rebuilds TwiML responses with the new token.
  2. **Transition gap:** any call that was mid-flight when the restart happened will drop; acceptable because rotations are rare and deliberate. No need for dual-token validation.
- **Local dev:** `.env` file, gitignored. `.env.example` has empty value with a comment pointing to `openssl rand -base64 32`.

### 2.4 Validation in the WS handler

In `relay.js`, the current flow is:

```js
twilioWs.on('message', (data) => {
  const msg = JSON.parse(data);
  switch (msg.event) {
    case 'start':
      streamSid = msg.start.streamSid;
      openaiWs = connectToOpenAI(twilioWs, streamSid, log);  // <-- this must NOT happen before auth check
      ...
  }
});
```

**Change:** before the `start` event's body runs, validate `msg.start.customParameters` against `STREAM_AUTH_TOKEN`. If invalid, close and return. Do not open the OpenAI connection.

```js
import { validateStreamAuth } from './middleware/ws-auth.js';

case 'start':
  const authResult = validateStreamAuth({
    customParameters: msg.start.customParameters,
    expectedToken: process.env.STREAM_AUTH_TOKEN,
    log,
    counters,
    reqId: msg.start.streamSid,
    sourceIp: /* captured at upgrade time, stored in closure — see below */,
  });
  if (!authResult.ok) {
    log.warn({ reqId: msg.start.streamSid, reason: authResult.reason, sourceIp }, 'WS auth rejected');
    counters.authRejectionsTotal++;
    twilioWs.close(1008, '');  // empty reason, no information leak
    return;
  }
  streamSid = msg.start.streamSid;
  openaiWs = connectToOpenAI(twilioWs, streamSid, log);
  break;
```

The `sourceIp` must be captured at WS upgrade time (in the `/twilio-media` route in `server.js`) and passed into `handleTwilioConnection`:

```js
fastify.get('/twilio-media', { websocket: true }, (socket, req) => {
  const sourceIp = req.ip;
  const reqId = req.id;
  fastify.log.info({ reqId, sourceIp }, 'Twilio Media Stream connected');
  handleTwilioConnection(socket, fastify.log, { sourceIp, reqId, counters });
});
```

**Signature update to `handleTwilioConnection`:**

```js
export function handleTwilioConnection(twilioWs, log, { sourceIp, reqId, counters })
```

**Case-insensitive parameter name lookup:** Twilio has historically been consistent in delivering `customParameters` with the exact case used in TwiML (`auth_token` → `auth_token`), but the Twilio Node SDK and some examples show camelCasing in different layers. The validator normalizes:

```js
function getParam(customParameters, name) {
  if (!customParameters) return undefined;
  const target = name.toLowerCase();
  for (const [k, v] of Object.entries(customParameters)) {
    if (k.toLowerCase() === target) return v;
  }
  return undefined;
}
```

### 2.5 Why not just IP allowlist

Blueprint already hints at this. Fleshed out: Twilio publishes media-server CIDRs at https://www.twilio.com/docs/sip-trunking/ip-addresses (these are for SIP but Media Streams egress from a similar pool; the exact ranges are not contractually stable). Relying on the IP list alone means:

1. Anyone else running on the same IP (shared cloud provider ranges) could impersonate Twilio.
2. A CIDR change without notice takes us offline until we notice and redeploy.
3. Does not protect against a misconfigured TwiML that points at us from someone else's Twilio account (someone with their own Twilio account could write TwiML with our WS URL and connect — the IPs would still be Twilio's).

The token in (2.2) defeats case 3 outright: another Twilio account doesn't have our `STREAM_AUTH_TOKEN`. It also defeats 1 without requiring a maintained CIDR list. We may add IP allowlist as a second layer later (defense-in-depth), but it is not a substitute. **Out of scope for v1.**

### 2.6 Close code rationale

`1008` (Policy Violation) is the correct WebSocket close code for a refused-because-of-auth connection. `1002` (Protocol Error) is wrong — the protocol was fine. `4xxx` codes are application-defined but less widely understood. The close reason string is empty — do not send `"bad token"` or similar, which leaks the check's existence to a probe.

## 3. Anti-replay considerations

Twilio signatures are stateless. Same URL + same params + same Auth Token ⇒ same signature, forever. An attacker who captures a valid `/twiml` POST (unlikely — it's over TLS, but assume log exfiltration) could replay it.

**Assessment for v1:** Replay of `/twiml` returns TwiML instructing Twilio to dial the WS URL. For a replay to cause actual harm:
1. Attacker would need to be on the same call's TCP session, OR
2. Attacker would need to trick our code into kicking off an OpenAI session from a static request.

Neither happens here. The `/twiml` endpoint is pure — it reads no state, writes no state, returns the same XML regardless of how many times it's called. The call session is gated by Twilio's own state (Twilio won't dial the WS unless it's mid-call), and the WS requires the token (which the replay wouldn't include in a way that helps the attacker, since they don't control the WS connection).

**Decision: no replay protection on `/twiml` for v1.** Documented residual risk: if an attacker ever obtains both a valid Twilio-signed POST body AND network position to redeliver it while controlling their own WS client, they could attempt to open a fresh WS session using the token from a replayed `/twiml`. But: the WS token is embedded in the *response*, not the request; replaying the request doesn't help them learn the token (the response goes back to wherever Twilio asks). So replay of `/twiml` leaks nothing.

Revisit this if/when we add tool-call endpoints that mutate state (e.g., `/tools/book-appointment` with a signed webhook). Those MUST have idempotency keys. Not in scope here.

## 4. Failure mode + observability

### 4.1 Logging rules (enforced by code review)

Every rejected request emits ONE structured warn log. The log object MUST contain:

| Field | Type | Source |
|-------|------|--------|
| `level` | string | `"warn"` (Pino default format) |
| `reqId` | string | Fastify request id (HTTP) or `streamSid` (WS) |
| `route` | string | `"/twiml"` or `"/twilio-media"` |
| `reason` | string enum | `"no-header"`, `"bad-sig"`, `"no-token"`, `"bad-token"`, `"server-misconfigured"`, `"body-not-string"` |
| `sourceIp` | string | `request.ip` (HTTP) or captured-at-upgrade `sourceIp` (WS) |
| `msg` | string | `"Auth rejected"` |

**MUST NOT contain (code review rejects):**
- The signature value (`X-Twilio-Signature` header)
- The token value (received or expected)
- The `TWILIO_AUTH_TOKEN` or any substring thereof
- The raw request body

Add a lint rule or at minimum a code-review checklist item: `grep` for `signature` and `token` in log statements within `middleware/`. The value of these should never be interpolated.

### 4.2 `/health` metrics

Extend the existing `/health` endpoint (currently returns `{status: 'ok'}`):

```js
const counters = {
  authRejectionsTotal: 0,
  // reserved for future: authRejectionsByReason (map)
};

fastify.get('/health', async () => ({
  status: 'ok',
  ws_registered: true,         // from blueprint §2
  active_connections: /* from WS plugin */,
  metrics: {
    auth_rejections_total: counters.authRejectionsTotal,
  },
}));
```

Counter is a plain in-memory integer. Resets on process restart. Good enough for now — if we need persistence we'll add Prometheus or similar later (out of scope).

`counters` is a single object instance passed by reference to both middlewares. Defined once in `server.js`, imported/passed as a factory argument.

### 4.3 What does NOT get logged

- Successful auths do not produce a dedicated log line. Request-level Pino logging at the Fastify level already emits an access log. No auth-specific success log.
- No metric for "successful auths" either — the Fastify access log is the source of truth; double-counting invites drift.

## 5. Boot sequence in `server.js`

Final order of operations:

```
1. Load dotenv
2. Assert required secrets (TWILIO_AUTH_TOKEN, STREAM_AUTH_TOKEN) — exit 1 if missing
3. Create Fastify instance with { logger: true, trustProxy: true }
4. Register @fastify/websocket
5. Register form-urlencoded parser (unchanged)
6. Initialize counters object
7. Build twilioSigHook via factory
8. Register routes:
   - GET /health
   - POST /twiml with preValidation: twilioSigHook

9. fastify.listen
```

## Integration points

- **Twilio webhook POST** → `/twiml` → signed with Auth Token → validated by `twilio-signature.js` → 200 TwiML or 403.
- **Twilio Media Streams WS** → `/twilio-media` → connects always (no handshake-time rejection; validate after `start` frame) → token in `start.customParameters.auth_token` → validated by `ws-auth.js` → proceed to OpenAI relay or close 1008.
- **OpenAI Realtime API** — no change; still connects only after successful Twilio auth.
- **Fly.io proxy** — headers `X-Forwarded-Proto` and `X-Forwarded-Host` consumed for URL reconstruction. Requires `trustProxy: true` in Fastify.

## Acceptance criteria

Each item must be independently checkable as true or false.

### HTTP signature validation
- [ ] `POST /twiml` with a valid `X-Twilio-Signature` (computed over reconstructed full URL + sorted params using `TWILIO_AUTH_TOKEN`) returns 200 with TwiML.
- [ ] `POST /twiml` with an invalid signature returns 403 with empty body (`Content-Length: 0`).
- [ ] `POST /twiml` with no `X-Twilio-Signature` header returns 403.
- [ ] `POST /twiml` with a signature built over `http://...` but forwarded via `X-Forwarded-Proto: https` is rejected 403 (proves we use XFP).
- [ ] `GET /twiml` returns 404 (route is POST-only).
- [ ] No log line emitted for any rejection contains the signature value, the token value, or the Auth Token.
- [ ] `TWILIO_AUTH_TOKEN` missing at boot → process exits 1 with a fatal log.
- [ ] `STREAM_AUTH_TOKEN` missing at boot → process exits 1 with a fatal log.
- [ ] Fastify is instantiated with `trustProxy: true`.

### TwiML response
- [ ] `/twiml` response contains `<Parameter name="auth_token" value="..."/>` inside `<Stream>`.
- [ ] The `value` attribute equals the current `STREAM_AUTH_TOKEN`, XML-escaped.
- [ ] WS URL uses `wss://` when the Host is not `localhost`, `ws://` when it is.

### WebSocket auth
- [ ] A WS connection to `/twilio-media` that sends a `start` frame with correct `auth_token` proceeds to open the OpenAI session.
- [ ] A WS connection that sends a `start` frame with missing `customParameters` is closed with code 1008 before any `media` frames are processed.
- [ ] A WS connection that sends a `start` frame with a wrong `auth_token` is closed with code 1008 before any OpenAI connection is opened.
- [ ] The token parameter lookup is case-insensitive on the key name (`auth_token` / `Auth_Token` both work).
- [ ] Token comparison uses `crypto.timingSafeEqual` on equal-length buffers; unequal lengths short-circuit to reject without throwing.

### Observability
- [ ] `/health` returns `metrics.auth_rejections_total` as an integer.
- [ ] Each rejection increments `auth_rejections_total` by exactly 1.
- [ ] Every rejection log contains `reqId`, `route`, `reason`, `sourceIp` and NOTHING confidential.

### Tests
- [ ] `npm test` runs node:test and all cases from §1.7 and §2.7 pass.
- [ ] Tests do not hit the network and do not require real Twilio or OpenAI credentials.

### Documentation
- [ ] `backend/README.md` has a "Security" section linking to this spec.
- [ ] `.env.example` contains `STREAM_AUTH_TOKEN` with the generation instruction comment; `TWILIO_WEBHOOK_SECRET` is removed.

## Out of scope (explicit)

- **Mutual TLS / mTLS between Twilio and Fly.** Twilio does not support client certs on webhook POSTs.
- **OAuth / JWT.** No user identity to bind; ingress is Twilio-only.
- **Signed URL scheme (option a).** Considered and rejected in §2.1.
- **IP allowlist (option c).** Considered and deferred as a possible future defense-in-depth layer.
- **WAF / rate limiting.** Fly's edge provides base DDoS mitigation. App-layer rate limiting (per-IP) is a separate concern, not required for correctness of auth.
- **Twilio Subaccount per client.** Multi-tenant isolation — separate future spec.
- **Call recording encryption / redaction.** Separate spec.
- **Prometheus / external metrics export.** In-memory counter is sufficient for v1; `/health` JSON is the exfil point.
- **Persistence of rejection counter across restarts.** Resets on process start — deliberate.
- **Automatic secret rotation.** Manual via `fly secrets set` + redeploy.
- **Per-call unique tokens.** Static shared secret per deploy is the decision; per-call tokens would require option (a) which was rejected.
- **Alerting on rejection spikes.** Future work once we have a metrics backend.

## Open questions (DECISION items, not coder guesses)

None that block implementation. The following are flagged for architect awareness but have chosen defaults:

1. **Token length / format.** Default: URL-safe base64 of 32 random bytes (~43 chars). Architect may override to a specific length or format. Default stands unless architect objects before coder begins.

2. **Boot-time secret length sanity check.** Default: reject anything shorter than 16 chars. Architect may tighten to 32. Default stands.

3. **Future IP allowlist layer.** Not in scope for this spec. If/when added, it stacks on top of the token check, not in place of it. Architect to decide scheduling.

4. **Rotation cadence.** No calendar-driven rotation. Architect to decide if/when to add one; current default is rotate-on-event only.

These are defaults, not guesses — coder implements as specified. If architect disagrees, spec revision comes first, then coder change.
